# Эксплуатация SQLite-режима CityQuest

Эта инструкция относится к односерверному SQLite-режиму текущего релиза. PostgreSQL HA, корпоративный вход и Kubernetes описаны в [PRODUCTION-HA.md](PRODUCTION-HA.md). SQLite backup/restore/admin CLI не применяются к PostgreSQL.

## Границы поставки

Это подготовленная к пилоту односерверная сборка. База SQLite хранится на локальном постоянном диске; один процесс приложения обслуживает оба города. `compose.production.yaml` запускает **одну реплику**, не обеспечивает HA, автоматическое переключение, распределённые сессии или непрерывное восстановление. Нельзя подключать несколько экземпляров приложения к общей SQLite через сетевую файловую систему. Геолокация браузера не доказывает физическое присутствие; коммерческие награды требуют дополнительной проверки.

Ниже описаны целевые процедуры. RPO ≤ 15 минут и RTO ≤ 60 минут — **цели пилота, не измеренные гарантии**. Они достижимы только при исправном расписании, независимой копии резервных данных, доступных ключах и регулярно отрепетированном восстановлении. Docker/HTTPS в среде подготовки не запускались: их нужно проверить на целевом Linux-хосте. CI собирает образ, когда изменения загружены в GitHub и Actions разрешён.

## Запуск на Linux

1. Установите Docker с Compose v2 и Caddy как службу хоста. Выделите домен; направьте DNS на сервер. Разрешите входящие 80/443, административный доступ ограничьте. Приложение слушает **127.0.0.1:3000**, не публичный интерфейс.
2. Создайте приватную конфигурацию командой `npm run env:production -- --origin https://quest.example.com --admin admin@example.com`, заменив домен и email своими. Генератор создаёт новый `.env.production` с правами 0600, случайным паролем администратора и ключами; **не перезаписывает существующий файл и не выводит секреты**. Прочитайте пароль локально из созданного файла. `--origin` принимает HTTPS origin без завершающего `/`, пути и query. При необходимости выберите новый путь через `--output`; для Compose задайте соответствующий `APP_ENV_FILE`. `.env.production.example` — справочник без секретов, `.env.example` — только development. Production требует настройки MFA администратора.
3. Генератор устанавливает `NODE_ENV=production`, `COOKIE_SECURE=true`, `REQUIRE_ADMIN_MFA=true`, `TRUST_PROXY=loopback`, 30 минут простоя сессии, JSON-логи и **три независимых** секрета: `DATA_ENCRYPTION_KEY` (MFA и переписка питомца), `AUDIT_HMAC_KEY` (аудит), `BACKUP_ENCRYPTION_KEY` (backup). Каждый — 32 случайных байта в 64 hex-символах. Сохраните ключи в защищённом независимом хранилище; не включайте их в Git и отчёты. Сгенерированный `DATABASE_PATH=./data/almaty.sqlite` подходит локальному Node.js; Production Compose всегда переопределяет его на `/app/data/almaty.sqlite` внутри постоянного тома.
4. Настройте Caddy по `Caddyfile.example`, заменив домен на значение `PUBLIC_ORIGIN`. Проверьте `caddy validate --config /etc/caddy/Caddyfile`; включите службу Caddy. Автоматическая выдача TLS требует доступного домена и портов 80/443.
5. Запустите:

```sh
docker compose --env-file .env.production -f compose.production.yaml up --build -d
docker compose --env-file .env.production -f compose.production.yaml ps
curl --fail http://127.0.0.1:3000/api/ready
curl --fail https://quest.example.com/api/health
```

Production Compose использует Linux `network_mode: host`, чтобы Caddy и приложение общались через настоящий loopback; эта конфигурация не является переносимой схемой для Docker Desktop. Локальная разработка использует `compose.yaml`. Все процессы с доступом к хосту входят в границу доверия reverse proxy: не размещайте здесь недоверенные приложения. `TRUST_PROXY=loopback` нельзя заменять безусловным доверием к клиентским `X-Forwarded-*` заголовкам.

Образ запускается UID/GID 1000, корневая ФС read-only, разрешён том `/app/data` и ограниченный tmpfs `/tmp`. Включены `init`, SIGTERM, 30 секунд на завершение, ограничения памяти/CPU/PID, удалены capabilities. Журналы Docker ограничены тремя файлами по 10 MB. Новый именованный том получает владельца каталога из образа; при подключении существующего тома администратор должен заранее обеспечить UID 1000 права записи. Не используйте `chmod 777`.

## Обновление SQLite с v0.4 на v0.5

Схема SQLite меняется с 3 на 4. До запуска нового образа остановите приложение и импортирующие процессы, создайте проверенный backup прежней базы, сохраните прежний образ и encryption/audit keys. Первый запуск v0.5 применит локальную additive-миграцию; отдельная PostgreSQL-команда миграции в этом режиме не нужна. Проверьте `/api/ready`, вход/MFA, старые квесты, питомца, новые маршруты и модерацию фотографии. Не запускайте старый v0.4 поверх обновлённого файла. Down-migration не поставляется: откат требует совместимого образа и восстановления backup в новый файл; новые записи после backup нужно сохранить/перенести отдельно.

Фотографии v0.5 входят в ту же SQLite и её backup. Начальный `PHOTO_STORAGE_LIMIT_MB=100` ограничивает только нормализованные JPEG; base64, таблицы и журнал занимают дополнительное место. `PHOTO_DAILY_UPLOAD_LIMIT=5` и `PHOTO_RETAINED_LIMIT=20` ограничивают успешные загрузки и сохранённые изображения одного пользователя. Добавьте параметры из `.env.production.example` при необходимости изменить значения; значения по умолчанию действуют и без них. Увеличение лимита требует повторного измерения места и времени восстановления. Удаление снимка из live-базы не удаляет его из старых backups; политика хранения должна учитывать фотографии и переписку. Подробности — в [PHOTO-CONTESTS.md](PHOTO-CONTESTS.md).

## Наблюдаемость и инциденты

- `/api/health` — процесс отвечает; `/api/ready` — проверка готовности. Docker healthcheck опрашивает ready каждые 30 секунд. Сам по себе статус unhealthy не перезапускает контейнер: настройте внешний мониторинг и дежурство.
- `/api/admin/metrics` доступен авторизованному администратору. Не публикуйте административную сессию в конфигурации публичного мониторинга. Метрики в памяти процесса сбрасываются при рестарте.
- Сигналы пилота: недоступность ready > 2 минут, устойчивые 5xx, рост p95, заполнение диска > 80%, отсутствие успешной **внешней** резервной копии > 20 минут. Пороги необходимо пересмотреть после измерений.
- При инциденте сохраните время, request ID и необходимые логи; не выгружайте пароль, cookie, MFA-секрет и точную историю передвижений в тикет. Ограничьте операции записи, если повреждена база или аудит; создайте резервную копию для расследования и восстанавливайте в отдельный файл.
- Перед обновлением: проверить тесты, сделать backup, записать версию образа/архива, убедиться в наличии ключей. Изменения схемы могут быть необратимыми для старой версии: rollback кода выполняется вместе с соответствующей резервной копией базы, а не запуском старого кода поверх новой схемы.

## Остановка и обновление процесса v0.7

При SIGTERM/SIGINT приложение переходит в draining: readiness отвечает 503, HTTP listener прекращает принимать новые соединения, а новые циклы maintenance больше не запускаются. `close()` сначала ожидает закрытия HTTP-сервера, затем завершения уже принятых асинхронных обработчиков и выполняющейся очистки. Только после этого закрывается принадлежащая приложению БД. Закрытие клиентского сокета само по себе не означает окончания обработчика: запрос AI или декодирование фотографии могут ещё выполняться.

Через 10 секунд после сигнала оставшиеся HTTP-соединения принудительно закрываются. Это ограничивает ожидание сокетов и не отменяет бизнес-операцию. Compose устанавливает внешний `stop_grace_period: 30s`; Kubernetes — 40 секунд вместе с пятисекундным preStop. После внешнего предела оркестратор может завершить процесс через SIGKILL: бессрочного graceful shutdown и гарантии завершения всех запросов нет. Подберите grace period по измеренному времени обработки и отдельно испытайте SIGTERM во время AI, загрузки фото, транзакции и maintenance на staging.

После обрыва во время записи результат для клиента может быть неизвестен. Перед повтором проверьте серверное состояние награды, голоса, заказа или фотографии; общий автоматический повтор мутаций не применяется. Для обновления SQLite остановите прежний процесс перед запуском нового. v0.7 сохраняет SQLite-схему 5, но backup, проверка восстановления и smoke после замены остаются необходимыми.

## Резервные копии

`scripts/backup.mjs` использует [online backup API Node SQLite](https://nodejs.org/api/sqlite.html#sqlitebackupsourceDb-path-options). Снимок включает зафиксированные данные WAL. Прямая файловая копия работающей `*.sqlite` **не используется**. Проверяются `PRAGMA integrity_check` и `PRAGMA foreign_key_check`; приватный снимок переводится в DELETE journal mode перед шифрованием, чтобы не оставлять незашифрованные WAL/SHM. Приложение при этом продолжает работать, но интенсивные записи могут увеличивать время резервирования.

```sh
# Локально; отдельная новая директория обязательна, старые копии не затираются.
node --env-file-if-exists=.env scripts/backup.mjs --database ./data/almaty.sqlite --output ./backups/manual-001

# На production, env контейнера уже содержит ключ и DATABASE_PATH.
# workdir задаёт каталог /app/data/backups для автоматически уникального имени.
docker exec --workdir /app/data cityquest-app node /app/scripts/backup.mjs
```

Результат — JSON с полным путём новой директории. В ней `manifest.json` и `snapshot.sqlite.enc` при наличии ключа, иначе `snapshot.sqlite`. Manifest содержит размер, SHA-256 файла, SHA-256 SQLite, время, формат и параметры AES-256-GCM. В production отсутствие или неправильный формат `BACKUP_ENCRYPTION_KEY` приводит к отказу. SHA-256 обнаруживает повреждение, но сам по себе не подтверждает авторство: доступ к копиям и manifest должен быть ограничен. AES-GCM проверяет подлинность зашифрованного содержимого при восстановлении.

Каталог имеет права 0700, файлы 0600. Временные файлы удаляются при штатно обработанных ошибках. При аварии питания/принудительном SIGKILL до завершения возможна неполная директория со снимком: она не считается успешной копией без manifest и проверки восстановления; хранение backup должно находиться на зашифрованном диске с ограниченными правами. Копии на том же диске защищают от части ошибок приложения, **не от потери хоста**.

Настройте host systemd timer каждые 15 минут с `ExecStart=/usr/bin/docker exec --workdir /app/data cityquest-app node /app/scripts/backup.mjs`, `OnCalendar=*:0/15`, `Persistent=true`. Контролируйте ненулевой exit code, длительность и возраст последней внешней копии. Загрузку в независимое защищённое объектное хранилище/резервный сервер настройте отдельным шагом только после успешного выполнения. Интеграция с конкретным облачным провайдером здесь не настроена.

Предлагаемая политика хранения: все 15-минутные копии за 48 часов, ежедневные за 30 дней, ежемесячные за 12 месяцев; сроки согласуются с реальными требованиями хранения данных. Автоматическое удаление в скрипт намеренно не встроено: сначала подтвердите внешнюю копию и проверку восстановления, затем примените lifecycle policy в хранилище. Минимум ежемесячно проводите полное восстановление на изолированном стенде и фиксируйте фактические RPO/RTO, размер базы и версию приложения.

## Восстановление без перезаписи

`restore.mjs` принимает директорию backup, проверяет manifest, размер и SHA-256, расшифровывает во временный приватный каталог, проверяет SQLite SHA-256, `integrity_check` и `foreign_key_check`, затем атомарно устанавливает **новый** файл. Существующая база и её WAL/SHM/journal никогда не перезаписываются. Параметра `--force` нет. Если `--output` не указан, создаётся уникальный путь `data/restored-*.sqlite`. Восстановление не импортирует сервер, не применяет миграции и не создаёт пользователей.

```sh
node --env-file-if-exists=.env.production scripts/restore.mjs --input ./backups/manual-001 --output ./data/restored-001.sqlite
```

При восстановлении в production:

1. Остановите приложение и фоновые импорты: `docker compose --env-file .env.production -f compose.production.yaml stop app`. Сохраните исходный том для расследования; не удаляйте live WAL вручную.
2. Поместите проверенную резервную директорию в существующий том `/app/data/backups/<id>` (или используйте изолированный новый том), убедитесь в правах UID 1000. Запустите разовый контейнер из **той версии образа, с которой совместима база**, не поднимая сервер:

```sh
docker compose --env-file .env.production -f compose.production.yaml run --rm --no-deps app node scripts/restore.mjs --input /app/data/backups/manual-001 --output /app/data/restored-001.sqlite
```

3. В `compose.production.yaml` измените `environment.DATABASE_PATH` на `/app/data/restored-001.sqlite` (или задайте его отдельным Compose override). Значение из `.env.production` здесь намеренно перекрывается Compose, поэтому одной смены env недостаточно. Используйте тот же `DATA_ENCRYPTION_KEY` и `AUDIT_HMAC_KEY`, которые соответствуют базе; секрет backup может отличаться от текущего и должен соответствовать данной копии. Запустите `docker compose --env-file .env.production -f compose.production.yaml up -d --force-recreate app`.
4. Проверьте `/api/ready`, вход с MFA, организации/квесты обоих городов, роли бизнеса, переписку питомца, приключения, доступ к одобренной и приватной фотографии, лимит фото и аудит. Сверьте контрольную точку аудита с независимо сохранённой записью. Не признавайте восстановление успешным только по HTTP 200.
5. Зафиксируйте длительность и потерянный интервал данных, затем возобновите запись и расписание backups. Сохраняйте предыдущий том до окончания расследования и согласованного срока хранения.

**Ключи восстанавливаются отдельно.** Database backup не содержит `.env.production` или файл development `data/security-keys.json`. Потеря `DATA_ENCRYPTION_KEY` делает сохранённые MFA-секреты и переписку питомца нечитаемыми; потеря `AUDIT_HMAC_KEY` препятствует проверке истории аудита; потеря backup key делает зашифрованную копию невосстановимой. Резервируйте ключи в независимом защищённом хранилище с контролем доступа. Для dev восстановление на другом компьютере также требует соответствующего `security-keys.json`; не добавляйте его в дистрибутив.

## Ротация секретов

- `BACKUP_ENCRYPTION_KEY`: создайте новый случайный ключ, сохраните предыдущий под его идентификатором, обновите секрет приложения/backup job и пересоздайте контейнер. Сделайте и восстановите новую копию. Старый ключ хранится до истечения срока хранения всех зашифрованных им копий. Manifest содержит `keyId` — первые 16 hex-символов SHA-256 ключа для выбора версии, сам ключ в manifest отсутствует.
- `DATA_ENCRYPTION_KEY` и `AUDIT_HMAC_KEY`: **простая замена env недопустима**. Она нарушит чтение MFA/переписки питомца или проверку старого аудита. Автоматическая миграция ключей в этой версии не реализована; нужна отдельная версионированная процедура перешифрования/переподписания с проверкой и архивированием прежней цепочки. До её разработки используйте защищённое хранение, ограниченный доступ и план реагирования при компрометации.
- Удалите bootstrap-пароль администратора из активной конфигурации после первоначального создания, сохраняя рабочий путь восстановления доступа согласно README. Не храните recovery-коды MFA вместе с паролем.

## Воспроизводимая проверка нагрузки

```sh
# Изолированная временная база с комплектными данными; удаляется после завершения.
node scripts/load-test.mjs --city astana --duration 10 --concurrency 4 --rps 8 --output ./reports/astana-local.json

# Отдельно запущенное локальное приложение; база не изменяется harness-ом.
node scripts/load-test.mjs --url http://127.0.0.1:3000 --city almaty --duration 30 --concurrency 8 --rps 20 --output ./reports/almaty-server.json
```

По умолчанию разрешены только `localhost`, `127.0.0.1`, `[::1]`. Для удалённого принадлежащего вам стенда нужно явно передать `--allow-remote`; никаких тестов сторонних сервисов, картографических тайлов или чужих API. Перенаправления запрещены. `--rps 0` снимает ограничение частоты; используйте только в контролируемом стенде. Приложение может отвечать 429 — отчёт считает их ошибками, лимиты для улучшения результата автоматически не отключаются.

Harness циклически запрашивает `/api/health`, `/api/config`, `/api/quests?city=...`, `/api/organizations?city=...`, читает ответ полностью и учитывает HTTP/network/JSON ошибки. Выводит p50/p95/p99, среднее, число запросов в секунду, статусы, ошибки и данные окружения. Все запросы включают выбранный city. Значения задержек включают ошибочные ответы; фактическая частота может быть ниже заданной из-за лимита параллельности. Файл отчёта не перезаписывается, при ошибках exit code ненулевой.

Это **read-only smoke/load harness**, без warm-up и без утверждений о максимальной ёмкости. Ephemeral-режим использует один процесс для сервера и генератора нагрузки; результаты не равны отдельному production-серверу. В нём не измеряются карта/Three.js/FPS, GPS, мобильная сеть, массовая авторизация, выдача наград, импорт, конкурентные записи, длительные сессии, мультиплеер или отказоустойчивость. Для enterprise-приёмки нужны отдельный генератор нагрузки, согласованный профиль действий, целевой сервер, реалистичный объём данных, продолжительный soak-test и проверка восстановления.

### Фактический локальный прогон 23 сентября 2026

Два последовательных независимых запуска, каждый с новой временной базой: Linux x64, Node.js v24.19.0, 9 логических CPU по `os.cpus()` в общей среде разработки. База каждого запуска содержит 13 128 организаций и 24 квеста обоих городов; запросы фильтруются по одному городу. Генератор и сервер в одном процессе, warm-up отсутствует. Запрошено 15 секунд, максимум 8 одновременных запросов и фиксированная частота 40 запросов/с. На каждый из четырёх endpoints пришлось по 150 запросов. ## Проверенные свойства и оставшиеся проверки

`node --test tests/operations.test.mjs` проверяет согласованный backup при активном WAL и незавершённой транзакции, шифрование/дешифрование, отсутствие незашифрованных sidecars, неверный ключ, повреждённый payload/SQLite, отказ от перезаписи, path traversal в manifest, учёт ошибок нагрузки и запрет внешних целей по умолчанию. Дополнительные регрессии `tests/u7-ops.test.mjs` проверяют отказ от backup/restore при нарушенных внешних ключах даже с корректными страницами и SHA-256, а также удаление отклонённых временных копий. Используются временные каталоги ОС, реальные пользовательские данные не нужны.

`node --test tests/init-env.test.mjs` проверяет независимость и формат ключей, случайный пароль, production-настройки, права файла, отказ от перезаписи, отклонение неканонического origin/email-инъекции и отсутствие секретов в stdout/stderr CLI. Реальный `.env.production` в дистрибутив не включён.

Перед публичным пилотом остаются проверка Docker и Caddy на сервере, внешняя доставка backups, испытание полного disaster recovery, сканирование образа и закрепление образа по digest, проверка восстановления MFA/аудита, мониторинг и дежурство, browser/device QA и профиль нагрузки с записями. Полноценный enterprise/HA потребует другого уровня инфраструктуры; эта сборка не заявляет его наличия.


## Обновление SQLite с v0.5 на v0.6

Перед обновлением остановите writers, создайте и проверьте backup, сохраните исходные ключи. Схема меняется с 4 на 5: локальная миграция добавляет индексы `006-query-indexes.sql`; она не удаляет прогресс и фотографии. На большой копии сначала измерьте время и место построения индексов. Первый запуск нового процесса применяет миграцию SQLite; PostgreSQL CLI к этому файлу неприменим. Старое приложение не запускайте поверх обновлённого файла. Откат выполняйте через восстановление совместимого backup в новый файл с прежним образом.

## Публичный релиз v0.7

После отдельного bootstrap и настройки MFA удалите `ADMIN_PASSWORD` из runtime env и выполните `node --env-file=.env.production scripts/production-check.mjs --database`. Команда открывает существующую SQLite read-only, не меняет схему и не добавляет seed. Отсутствующая база, несовместимая схема, незаполненные контакты/документы, примерные домены, отсутствие администратора с MFA и несогласованный фото-ledger приводят к ненулевому exit code. Обязательные действия площадки и новые лимиты — в [PRODUCT-LAUNCH.md](PRODUCT-LAUNCH.md).
